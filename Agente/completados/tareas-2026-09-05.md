## Studio (nakomi.studio) — restauración de la capa de negocio desde dump weekly 23/08

**ID / origen**: seguimiento del incidente de backups 2026-08-27 (pendiente "restaurar studio").

### Qué se hizo
- Se confirmó que la BD viva de studio tenía la capa de negocio **vacía** (projects=0, users=0,
  orders=0): la pérdida real ocurrió **entre el 23/08 y el 30/08** (corrige la estimación previa
  de 28/08–05/09). El `db-compare` del 28/08 fue un **falso negativo**: comparaba contra el dump
  27/08 (que sí tenía datos), enmascarando el vaciado posterior.
- Se comprobó que el dump 27/08 (7 proyectos) ya **no existe** (rotado por `daily_keep=2`). El
  único dump con datos superviviente es `weekly/2026-08-23_0100.sql.gz` (6 projects, 13 users,
  1 order).
- Tras autorización del usuario, se restauró el **catálogo + negocio + chat + hosting 23/08**
  completo (44 tablas) en la BD viva.

### Método (restore de dump `.sql.gz` del sistema VPS)
- No existe comando `restore` del manager para los dumps `.sql.gz` del sistema VPS (el `restore`
  del manager solo lee su propio formato `.tar.gz`).
- Generación del SQL en el VPS vía `host-exec`: python3 extrae los bloques `COPY public.<tabla>`
  de las 44 tablas objetivo del dump → SQL = `BEGIN; SET LOCAL session_replication_role = replica;
  DELETE ×44; COPY ×44; COMMIT`.
- Ejecución: `docker cp` del SQL al contenedor postgres (`0e0ea7cc601c`) + `psql -v
  ON_ERROR_STOP=1 -f`. `rust_app` es superusuario → `session_replication_role=replica` disponible.
- Esquema verificado sin deriva: dump y BD viva comparten 69 migraciones (max `20260726200000`).

### Decisiones / gotchas
- **GOTCHA host-exec**: `docker exec` interno **sin `timeout N` se cuelga** contra el límite del
  manager. Usar siempre `timeout N docker exec ...` en scripts vía `host-exec`.
- Los 2 projects draft del dump (Guillermo Chatbot, Material de Pádel) no aparecen en `/api/projects`
  (filtro `published`) — comportamiento esperado, no pérdida.
- Encoding: el título "Material de Pálidel" se guarda correctamente como UTF-8 (hex `c3a1`); el
  `P├í` visto en terminal Windows es solo un problema de visualización del codepage, no de datos.
