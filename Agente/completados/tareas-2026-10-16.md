## 16AA-12 — El `.exe` se compila en la VPS 89 (cross-compile a Windows)

El portátil dejó de compilar Rust el 2026-10-16 (AGENTS §1): la toolchain se
retiró entera. `workspace-manager/scripts/actualizar-coolify-manager.ps1:38`
hacía `cargo build --release` en local y ya no podía.

- **Cambio.** `scripts/build-windows.mjs` (nuevo), mismo patrón ya probado de
  `limpiador-pc/scripts/build-windows.mjs`: fuente -> 89 -> `.exe` de vuelta.
  Compila con `cargo xwin build --release --target x86_64-pc-windows-msvc` bajo
  `cm-heavy`, con `-C target-feature=+crt-static` para no depender de la
  redistribuible de Visual C++. La copia remota vive en `/var/tmp` (la barre
  `cm-sweep`); lo persistente es el toolchain de la 89. El `.exe` vuelve por
  `ssh cat` (con `scp`, una ruta local `C:\...` se confunde con `host:ruta`) y se
  valida por cabecera `MZ`.
- **Qué NO viaja.** `config/settings.json` y sus copias (credenciales, AGENTS §2)
  y `.cargo/`, cuyo `config.toml` fija un `target-dir` de Windows que en Linux
  sería un directorio relativo absurdo. `config/templates/` sí: `contexto.rs` lo
  incrusta con `include_str!`.
- **Fricción encontrada.** El C de `ring` no compilaba:
  `error occurred in cc-rs: failed to find tool "llvm-lib"`. cc-rs busca el
  archivador sin versión y en Ubuntu solo existe `/usr/bin/llvm-lib-18`. Enlace
  `~/.local/bin/llvm-lib` -> `/usr/bin/llvm-lib-18`, y ese directorio delante en
  el PATH del build remoto.
- **Evidencia.** `node scripts/build-windows.mjs` -> 22 247 424 B con cabecera
  `MZ` (3m 50s el primer build, 1m 39s incremental). Publicado y comprobado por
  `workspace-manager/scripts/actualizar-coolify-manager.ps1`:
  `OK: coolify-manager 1.0.0 (commit e816ac1)`. La tab vps del manager lo ve:
  `GET /api/vps/config` -> `{"version":"coolify-manager 1.0.0","ok":true}`.

## 16AA-12b — Los 5 hallazgos del gate de `build_laptop` (código de F4)

Al cerrar 16AA-12 el gate de este repo salió con 5 hallazgos **heredados** (código
de F4, 13-14 oct, commit `6bf110f`; la base del gate era del 12-10, de ahí que
aparecieran como nuevos). Se corrigieron en vez de baselinarlos.

- **Refactor (3).** `dispatch_build_laptop` pasó de 8 parámetros sueltos a un
  struct `ArgsBuildLaptop`. `compilar_en_builder` (121 líneas) se partió en
  `comprobar_docker` + `preparar_sitio_remoto` + `lanzar_build_remoto` +
  `guardar_tgz_remoto`, con `SitioRemoto` para las rutas del build host;
  `execute` (171 líneas) en `resolver_build_host` + `preparar` +
  `ejecutar_en_builder` + `ejecutar_en_laptop`, con `Preparado` para lo resuelto
  antes de compilar. Sin cambios de comportamiento.
- **Rutas (2).** `tarball_path` pasa por `join_segmento_seguro` (rechaza
  separadores y `..` y comprueba con `canonicalize` + `starts_with` que el tgz no
  salga del workdir) y devuelve `Result`. `clave_laptop` comprueba lo mismo para
  la clave SSH, pero **devuelve la ruta original**: canonicalizar para el valor
  de retorno metería el prefijo verbatim `\\?\C:\...`, que es justo lo que deja
  colgado al cliente docker (ver `execute_file`).
- **Evidencia.** `Arranque gate "coolify-manager-rs" --cierre` -> 0 nuevos, 0
  resueltos (base 0). El análisis de la 89 no está vacío: `GET
  /api/gate/analisis?clave=coolify-manager-rs` -> `estado: "ok"`, `hallazgos: []`.
  `node scripts/build-windows.mjs` compila cruzado a Windows en 1m 43s sin
  avisos; `cargo xwin test --no-run` compila los módulos de test. Los tests no se
  pueden **ejecutar**: el `.exe` es de Windows y `cargo test` nativo en Linux no
  compila (`bollard::Docker::connect_with_named_pipe` es solo de Windows).
- **Decidido.** Se refactoriza, no se baselinea: los tres de tamaño eran deuda
  real y los dos de ruta se resuelven con el helper que ya existía
  (`validation::join_segmento_seguro`).
